# 17 — Живое обновление через SSE

**What to build:** Двое открыли один и тот же `/plan/{id}`. Первый перетаскивает
бар — у второго диаграмма приезжает к новому состоянию сама, без перезагрузки.
То же самое для правки агентом, импорта и отката.

Клиент держит SSE-подписку. Сервер подписывается на канал Honker и пересылает
события подписчикам этого Plan. Клиент сравнивает пришедшую версию со своей и,
если отстал, перезапрашивает Plan целиком — событие остаётся сигналом, а не
данными.

⚠️ `db.listen` начинает с текущего `MAX(id)` и историю не переигрывает. Значит
**первый кадр SSE обязан нести текущую версию Plan**: клиент, подключившийся уже
после чужой правки, иначе останется устаревшим навсегда. Это ровно та дыра,
из-за которой в первой редакции дизайна требовался durable stream — здесь она
закрывается одним кадром на подключении.

Примечание по тестированию: `starlette.testclient.TestClient` и голый
`httpx.ASGITransport` не годятся для этого сценария — их in-memory ASGI-транспорт
сигналит `http.disconnect` сразу после отправки тела GET-запроса, из-за чего
generator обрывается после первого кадра ещё до того, как второй клиент успевает
записать. Тесты SSE поднимают настоящий `uvicorn.Server` на случайном порту в
фоновом потоке (`tests/test_sse.py::_LiveServer`) и подключаются реальным HTTP.

## Найден и исправлен дефект (P1-2), 2026-09-01

Пункт «Первый кадр после подключения несёт текущую версию Plan» был отмечен
done, но реализация не давала заявленной гарантии. `PlanNotifier.listen` был
`async def ... yield`-обёрткой: тело выполняется только на первом `__anext__`,
т.е. после того как `plan_events` уже прочитал версию для первого кадра и
отправил его клиенту. Настоящий honker `Listener` (со своим `MAX(id)`) при этом
конструировался позже, чем документация тикета утверждала. Запись, случившаяся
между вызовом `service.notifier.listen(...)` и реальным конструированием —
т.е. между отправкой первого кадра и входом в `async for` — терялась: её id уже
был `<= last_seen` к моменту, когда `Listener` наконец подписывался.

Исправлено: `PlanNotifier.listen` теперь синхронный метод, возвращающий уже
сконструированный (и уже подписанный) `honker.Listener` немедленно —
`gaintt/notifications.py`. `plan_events` в `gaintt/main.py` не изменил
порядок вызовов (он и был правильным), но теперь эта гарантия реальна.

Регрессия закрыта двумя тестами:
- `tests/test_notifications.py::test_listen_subscribes_synchronously_not_on_first_iteration`
  — детерминированный тест на уровне `PlanNotifier`, без HTTP: пишет ПОСЛЕ
  вызова `listen()` и ждёт, что событие всё равно дойдёт.
- `tests/test_sse.py::test_sse_write_between_subscribe_and_first_frame_is_delivered`
  — HTTP/SSE-тест поверх настоящего `uvicorn`, детерминированно инжектирует
  конкурентную запись изнутри монки-патченного `service.get_plan` (том самом
  месте, где `plan_events` читает версию для первого кадра), а не полагается
  на реальный тайминг.

Оба теста были проверены на падение на добаговом коде (временный откат
`PlanNotifier.listen` к `async def ... yield`) — оба падали по описанной выше
причине (таймаут ожидания второго кадра / события).

## Найден и исправлен дефект (P1-3), 2026-09-01

«То же самое для правки агентом, импорта и отката» из шапки тикета не
выполнялось для импорта: `/api/import` вызывал `service.replace_member_plan`,
который создавал **новый** Plan (новый uuid) и делал его текущим только для
импортировавшего — остальные участники оставались на старом Plan, сигнал не
публиковался, а URL уже открытых вкладок продолжал указывать на прежний,
неизменившийся Plan.

Исправлено: `/api/import` теперь принимает `plan_id` (multipart-поле),
проверяет членство и вызывает новый `PlanService.import_into_plan(plan_id,
imported)`, который заменяет содержимое **того же** Plan (тот же id, версия
+1) и публикует сигнал как любая другая запись — так что открытые вкладки
других участников подхватывают импорт тем же SSE-путём, без специального
случая. `replace_member_plan` удалён как источник дефекта.

Регрессия закрыта:
`tests/test_http.py::test_import_replaces_the_open_plan_in_place_and_is_visible_to_another_member_without_reload`
(и соседний `test_import_requires_membership_and_a_stranger_cannot_import_into_a_plan`
на проверку доступа). Проверено падением на добаговом коде (временный откат
`import_into_plan`/`/api/import` к `replace_member_plan`) — падало именно на
`imported.json()["plan"]["id"] == plan["id"]`, т.е. по причине новой мнимой
подмены Plan.

Фронтенд (`frontend/src/App.tsx`, `uploadFile`) обновлён отправлять `plan_id`
вместе с файлом; регрессия на рассинхрон контракта клиент/сервер закрыта
`frontend/src/App.test.ts` ("export and import wire the current plan_id").
